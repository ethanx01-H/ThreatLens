THREATLENS - CURRENT VERSION FIX PLAN
========================================

Purpose
-------
This document contains the recommended fixes for the current ThreatLens version,
with focus on export/reporting first, followed by logging, API handling, risk
assessment, testing, and later SOC integrations.

IMPORTANT:
Do not change everything at once. Make one change, test it, then continue.

============================================================
1. CURRENT EXPORTS - PRIORITY
============================================================

Keep:
  1. TXT  - Critical
  2. DOCX - Critical
  3. JSON - Critical

Optional later:
  4. CSV  - Medium
  5. PDF  - Later
  6. HTML - Later

Do not build separate investigation logic inside each exporter.

Recommended architecture:

                    Investigation Engine
                            |
                            v
                     Common Report Model
                            |
              +-------------+-------------+
              |             |             |
              v             v             v
             TXT           DOCX          JSON
          analyst view    formal SOC    automation

3. DOCX EXPORT - FORMAL SOC REPORT
============================================================

Make DOCX the professional investigation report.

Recommended structure:

[ ] Cover page
    - ThreatLens
    - Threat Intelligence Investigation Report
    - Target
    - Investigation ID
    - Classification
    - Generated date

[ ] 1. Executive Summary

[ ] 2. Target Information

[ ] 3. Risk Assessment

[ ] 4. Threat Intelligence

[ ] 5. DNS / WHOIS

[ ] 6. Network Reconnaissance

[ ] 7. Subdomains

[ ] 8. Related Indicators

[ ] 9. Investigation Timeline

[ ] 10. Detection Rules

[ ] 11. Recommended Actions

[ ] 12. Appendix / Raw Evidence


DOCX Executive Summary should show:

  Risk Score
  Classification
  Assessment / Verdict
  Confidence
  Intelligence Coverage
  Malicious Signals
  Mitigating Factors


Threat intelligence should use a table:

  Source | Status | Result | Details

Example:

  VirusTotal | CHECKED | MATCH | 5/92 detections
  AbuseIPDB | CHECKED | NO MATCH | 0 reports
  ThreatFox | MATCH | 2 IOCs | Malware family
  URLhaus | CHECKED | NO MATCH | Not listed
  OTX | CHECKED | MATCH | 3 pulses
  Shodan | ERROR | - | Rate limited


Detection rules should be separated:

  10.1 SIGMA
  10.2 ELASTIC KQL
  10.3 ELASTIC EQL
  10.4 SPLUNK
  10.5 JSON


Recommended Actions should depend on assessment/risk.

HIGH example:
  1. Search Elastic for historical sightings.
  2. Identify affected hosts and users.
  3. Review network connections.
  4. Investigate related domains/hashes.
  5. Consider blocking if malicious activity is confirmed.
  6. Create/update detection rules.

LOW example:
  1. Continue monitoring.
  2. No immediate blocking.
  3. Re-evaluate if new intelligence appears.

5. COMMON REPORT MODEL
============================================================

Important architectural fix:

Do NOT make TXT, DOCX and JSON independently understand the
investigation data.

Create one common report model:

  Investigation Engine
          |
          v
    InvestigationReport
          |
    +-----+-----+
    |     |     |
    v     v     v
   TXT   DOCX  JSON

Example conceptual model:

  report.target
  report.target_type
  report.investigation_id
  report.timestamp
  report.assessment
  report.sources
  report.dns
  report.whois
  report.network
  report.indicators
  report.detections
  report.actions

Then:

  export_txt(report)
  export_docx(report)
  export_json(report)


============================================================
6. LOGGING SUBSYSTEM
============================================================

Logging must be configurable from BOTH:

  GUI
  CLI

Both must use the SAME configuration.

Recommended configuration:

  ~/.threatlens/config.json

Example:

{
  "logging": {
    "enabled": true,
    "level": "INFO",
    "directory": "~/.threatlens/logs",
    "rotation": "daily",
    "max_size_mb": 10,
    "retention_days": 7,
    "console": true
  }
}

GUI settings:

  Enable Logging
  Log Level
  Log Location
  Rotation
  Maximum File Size
  Retention Days
  Console Logging
  Debug Logging

CLI examples:

  threatlens config logging
  threatlens config logging --level DEBUG
  threatlens config logging --retention 14
  threatlens config logging --max-size 20
  threatlens config logging --rotation daily
  threatlens config logging --disable
  threatlens config logging --enable

Recommended defaults:

  Enabled:        Yes
  Level:          INFO
  Rotation:       Daily
  Maximum Size:   10 MB
  Retention:      7 days
  Console:        Yes
  Debug:          No

Use rotating logging rather than unlimited files.

Do not log:
  - API keys
  - secrets
  - full API responses by default
  - unnecessary sensitive data

Application logs should contain operational events, not full investigation
reports.


============================================================
7. API ERROR HANDLING
============================================================

Do not treat every API failure as None.

Differentiate:

  SUCCESS
  NOT_FOUND
  NO_API_KEY
  RATE_LIMITED
  UNAUTHORIZED
  FORBIDDEN
  TIMEOUT
  SERVER_ERROR
  NETWORK_ERROR
  INVALID_RESPONSE

Recommended result model:

  source
  status
  data
  error
  http_status

Example:

  VirusTotal
    Status: RATE LIMITED
    HTTP: 429

versus:

  VirusTotal
    Status: CHECKED
    Result: NO MATCH

These must not be treated as the same condition.


============================================================
8. RISK ENGINE FIX
============================================================

Major issue:

Do NOT allow "known good" / whitelist logic to cap a score and
override strong malicious evidence.

Bad model:

  Known Good
      |
      v
  Cap score at 25

Better:

  Known Good
      |
      v
  Reduce weak/contextual signals
      |
      v
  Strong direct malicious evidence still wins

Example:

  Known-good infrastructure
  + ThreatFox direct IOC
  + URLhaus listing
  + VT malicious detections
  = potentially HIGH/CRITICAL

Whitelist should reduce false positives, not override strong evidence.


============================================================
9. ADD OVERALL UNKNOWN VERDICT
============================================================

Individual source results can remain:

  MALICIOUS
  BENIGN
  NOT CHECKED

Overall investigation should become:

  MALICIOUS
  SUSPICIOUS
  BENIGN
  UNKNOWN

Important:

"No intelligence found" does NOT automatically mean "BENIGN".

Example:

  VT          CHECKED / CLEAN
  AbuseIPDB   CHECKED / CLEAN
  OTX         NO MATCH
  ThreatFox   NOT CHECKED
  URLhaus     NOT CHECKED

Overall:
  UNKNOWN

This is safer for SOC investigations.


============================================================
10. ADD CONFIDENCE
============================================================

Separate:

  Risk Score
  Confidence
  Coverage

Example:

  Risk Score:   87/100
  Confidence:   94%
  Coverage:     6/7 sources
  Verdict:      MALICIOUS

Another example:

  Risk Score:   12/100
  Confidence:   31%
  Coverage:     2/7 sources
  Verdict:      UNKNOWN

Low risk + low confidence is NOT the same as low risk + high confidence.


============================================================
11. ADD SOURCE FRESHNESS
============================================================

For intelligence where timestamps are available, capture:

  first_seen
  last_seen
  source_updated
  observation_age
  freshness

Freshness levels:

  HIGH
  MEDIUM
  LOW

Fresh/current intelligence should have more influence than very old
intelligence.


============================================================
12. DOMAIN MULTIPLE-IP FIX
============================================================

Current behavior should not investigate only the first resolved IP.

Example:

  example.com
      |
      +-- 1.1.1.1 -> investigate
      +-- 2.2.2.2 -> investigate
      +-- 3.3.3.3 -> investigate

For each IP:
  DNS
  reputation
  ports
  HTTP/TLS
  intelligence

Then correlate results back to the domain.

============================================================
16. API KEY STORAGE
============================================================

Do not store API keys as plaintext JSON if avoidable.

Prefer OS credential storage:

  Windows -> Windows Credential Manager
  Linux   -> Secret Service / keyring
  macOS   -> Keychain

Python option:

  keyring

GUI and CLI should use the same credential backend.


============================================================
17. PORT / SERVICE DETECTION
============================================================

Do not send the same HTTP HEAD request to every open TCP port.

Use protocol-specific probes where appropriate:

  21   FTP
  22   SSH
  25   SMTP
  53   DNS
  80   HTTP
  443  HTTPS/TLS
  445  SMB
  6379 Redis
  9200 Elasticsearch

Output:

  PORT  SERVICE        VERSION        EVIDENCE
  22    SSH            OpenSSH        Banner
  443   HTTPS          nginx          TLS/HTTP
  9200  Elasticsearch  8.x            HTTP response
